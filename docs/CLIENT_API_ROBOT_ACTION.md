# 机器人动作消息接口文档

| 项目 | 内容 |
|---|---|
| **面向** | 客户端 / 固件 / 前端工程师 |
| **协议** | WebSocket（`ws://<host>:8000/xiaozhi/v1/`） |
| **消息方向** | 服务端 → 客户端（下行） |
| **版本** | v1（2026-10-02） |
| **关联文档** | [CLIENT_API.md](CLIENT_API.md)（完整客户端协议）、[DESIGN_STRUCTURED_OUTPUT.md](DESIGN_STRUCTURED_OUTPUT.md)（服务端设计） |

> **本文只讲机器人动作消息**（`type: "action"`）。连接、鉴权、音频格式、`hello`/`tts`/`stt` 等基础协议见 [CLIENT_API.md](CLIENT_API.md)。

---

## 1. 概述

服务端在播报语音的同时，会下发**肢体动作指令**，让机器人做出配合的姿势（挥手、鼓掌、敬礼等）。

```
                     ┌──────────────────────┐
   服务端 ─── action ──▶│  客户端              │───▶ 驱动舵机 / 播放动画
                     │  （接收、排队、执行）  │
   服务端 ─── tts/音频──▶│                      │───▶ 扬声器
                     └──────────────────────┘
```

**动作消息和语音是两条独立的通道**，互不阻塞。客户端不要等语音播完才处理动作。

---

## 2. 消息格式

```json
{
  "type": "action",
  "action": "WAVE",
  "session_id": "a1b2c3d4e5f6..."
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `type` | string | ✅ | 固定值 `"action"` |
| `action` | string | ✅ | 动作代码，取值见 §3 |
| `session_id` | string | ✅ | 会话 ID，同一次对话内保持一致 |

### 2.1 向前兼容要求

客户端**必须忽略不认识的字段**，不要因为出现新字段而报错或拒绝处理。

> 服务端将来可能追加字段（例如 `delay_ms`），届时老固件忽略即可，不影响现有行为。

---

## 3. 动作代码表

| 代码 | 含义 | 建议表现 |
|---|---|---|
| `NOACTION` | 无动作 | 保持不动（当前实现会下发这个值） |
| `WAVE` | 挥手打招呼 | 抬起单臂左右摆动 |
| `CLAP` | 拍手鼓掌 | 双手合击数次 |
| `THINK` | 思考动作 | 手托下巴，头部微倾 |
| `WELCOME` | 欢迎手势 | 双臂张开 |
| `POINT_LEFT` | 指向左 | 单臂指向左侧 |
| `POINT_RIGHT` | 指向右 | 单臂指向右侧 |
| `SALUTE` | 敬礼 | 抬手至额头 |

### 3.1 未知动作码的处理

**收到表中没有的动作码时，静默忽略，不要报错。**

服务端会新增动作码，老客户端遇到不认识的就跳过即可——这与 §2.1 的向前兼容要求一致。

> 服务端侧已保证：不会下发非法动作码。如果收到，说明协议版本不匹配或消息被篡改，跳过是安全的选择。

---

## 4. ⚠️ 关键行为：可能连续收到多条

> **状态：尚未上线。** 当前服务端一次回复最多下发 **1 条** `action` 消息；
> 多动作是后续改造目标（见 [VOICE_ACTION_OUTPUT.md](VOICE_ACTION_OUTPUT.md) §7）。
> 本节描述的是改造完成后的目标行为，客户端可以按此提前设计，但现在不会收到多条。

**这是本节最重要的一点。**

一句话可能配多个动作。服务端会把它们**拆成多条消息依次下发**，而不是发一条数组。

```jsonc
// t = 0ms
{"type": "action", "action": "WAVE",  "session_id": "abc123"}

// t = 800ms（服务端等待了 800ms 才发）
{"type": "action", "action": "THINK", "session_id": "abc123"}
```

### 4.1 客户端要做的

| 要求 | 说明 |
|---|---|
| **不能假设一次只收到一条** | 一次语音回复可能触发 0~3 条动作消息 |
| **按接收顺序执行** | 顺序即语义顺序 |
| **不要自己加延迟** | 服务端已经控制了发送间隔，客户端再等待会导致时序漂移 |
| **不要在两条消息之间插入等待** | 收到就执行 |

### 4.2 动作时长由谁决定

**服务端不知道每个动作实际执行多久**，它只按固定延迟下发。

| | 谁知道 |
|---|---|
| 何时发下一条 | 服务端（固定延迟，如 800ms） |
| 单个动作执行多久 | **只有客户端知道** |
| 动作是否播完 | 服务端不知道（不做回执，见 §8） |

这带来一个**需要客户端决策**的取舍，见 §5.2。

## 5. 客户端实现要点

### 5.1 三条硬性要求

**① 动作与语音并行，互不阻塞**

收到 `action` 消息时，**不要**等待 `tts` 状态或音频播放完成再处理。两者是独立的：

```
收到 action → 立刻驱动舵机/动画
收到 tts sentence_start → 立刻准备播放
（两条链路同时进行）
```

**② 打断后不要再启动新的动作**

> **两端都不存在动作队列。** 服务端解析出动作就立即下发，代码里<b>没有"动作队列"这个对象</b>；
> 客户端同样应当收到就执行（方案 A）。所以不存在"清空待执行队列"这个操作，
> 真正要做的是：打断之后不要再启动新的动作。

收到以下任一情况时，**之后到达的动作消息应当被忽略**：

| 触发条件 | 说明 |
|---|---|
| 客户端发出 `{"type":"abort"}`，并收到服务端回的 `{"type":"tts","state":"stop"}` | 用户打断，本轮对话作废 |
| `session_id` 发生变化 | 新的一轮对话，旧动作作废 |

> 正在执行中的那个动作可以播完，也可以立即中止——由客户端决定，服务端不做要求。

**③ 忽略未知字段和未知动作码**

见 §2.1 和 §3.1。

### 5.2 已确定：方案 A（收到即执行，两端都没有队列）

**场景**：`WAVE` 需要 2 秒，但服务端在 800ms 后就发来了 `THINK`。

| 方案 | 行为 | 是否采用 |
|---|---|---|
| **A. 打断当前，立即执行新的** | 收到即执行 | ✅ **当前实现即如此** |
| B. 排队，等前一个播完 | 依次完整执行 | ❌ 不采用 |

**这不是一个待定的取舍，而是已经确定的行为**：

- **服务端**：解析出动作就立即下发，代码里没有动作队列对象；
- **客户端**：应当收到就执行，同样不需要队列。

理由：服务端的 `delay_ms` 语义是「相对上一条动作的**下发时刻**」，而不是「相对上一条动作的**结束时刻**」。排队会让整体时序向后漂移，与协议语义不符。

> 因此 **§5.1② 的"清空队列"和 §5.3 的"队列超时丢弃"都不需要实现** —— 没有队列可以清，也没有东西会等待超时。

### 5.3 （不适用）队列超时保护

> **不适用。** 方案 A 下没有动作队列，不存在"动作在队列里等待超时"的问题。
> 若将来改成方案 B，再考虑这一条。

## 6. 完整交互示例

### 6.1 一次带多个动作的对话

**用户说**：「你好呀」

```
服务端                                客户端
   │                                     │
   │─ {"type":"stt","text":"你好"} ─────▶│  显示识别结果
   │─ {"type":"tts","state":"start"} ───▶│  准备播放
   │                                     │
   │─ {"type":"action","action":"WAVE"} ▶│  ★ 立刻挥手
   │─ {"type":"tts","state":"sentence_start",
   │    "text":"哈喽！我是小智..."} ─────▶│  ★ 开始播放语音
   │─ <二进制 opus 音频帧> ──────────────▶│
   │                                     │
   │        （约 800ms 后）               │
   │─ {"type":"action","action":"THINK"}▶│  ★ 转为托腮姿势
   │                                     │
   │─ {"type":"tts","state":"stop"} ────▶│  播放结束
   │                                     │
```

注意时间线：**动作和语音是并行的**，不是先动作后语音。

### 6.2 无动作的场景

**当前实现会在没有动作时下发 `{"action":"NOACTION"}`**，而不是完全不发消息。

```
{"type": "action", "action": "NOACTION", "session_id": "..."}
```

客户端收到 `NOACTION` 时保持不动即可，不需要任何视觉表现。

> 仍然不要反过来假设「每次对话必有 action 消息」——做防御性处理没有坏处。

### 6.3 被打断的场景

```
用户打断
   │
客户端 ─ {"type":"abort"} ─▶ 服务端
   │
   │◀─ {"type":"tts","state":"stop"} ──── 服务端确认中断
   │
   │   ★ 此刻应清空待执行的动作队列
   │
```

## 7. 与语音消息的关系

动作消息可能出现在一次回复的**任意时机**，客户端应能处理乱序到达：

| 可能的到达顺序 | 是否正常 |
|---|---|
| `action` → `tts/sentence_start` → 音频 | ✅ 常见 |
| `tts/sentence_start` → `action` → 音频 | ✅ 正常 |
| `action` → 音频 → `action` | ✅ 多动作场景 |
| 只有音频，没有 `action` | ✅ 无动作场景 |
| 只有 `action`，没有音频 | ⚠️ 异常，但仍应执行动作 |

**不要依赖固定顺序**，用消息类型判断而不是用到达位置判断。

---

## 8. 服务端不做什么

明确边界，避免客户端做多余等待：

| 服务端不做 | 说明 |
|---|---|
| ❌ 不等待动作执行完成 | 发完就继续，不管客户端 |
| ❌ 不接收动作执行回执 | 当前版本无反馈通道（见遗留事项） |
| ❌ 不感知动作实际时长 | 只用固定延迟推算 |
| ❌ 不在音频流里混入动作数据 | 动作是独立的 JSON 消息，不是音频附属信息 |

## 9. 兼容性说明

### 9.1 本次改造对客户端是透明的

服务端的 LLM 输出格式正在从「方括号标记」改为「JSON 结构化输出」，但**设备协议不变**：

| | 改造前 | 改造后 |
|---|---|---|
| LLM 输出 | `[语音回复:x][动作指令:WAVE]` | `{"voice":"x","actions":[{"code":"WAVE"}]}` |
| **客户端收到的消息** | `{"type":"action","action":"WAVE"}` | **完全相同** |
| 单动作 / 多动作 | 单动作 | 多动作（拆成多条消息，格式不变） |

**客户端无需改动即可继续工作。**

### 9.2 但客户端要利用多动作能力需要做的事

如果希望支持「一句话配多个动作」，客户端需要：

1. 确认能处理**连续收到的多条 action 消息**（§4）
2. 决定 §5.2 的取舍（打断 vs 排队）
3. 实现 §5.1 的打断清理逻辑

**如果客户端暂时不想支持多动作**：只执行第一条、忽略后续即可，不会出错。
